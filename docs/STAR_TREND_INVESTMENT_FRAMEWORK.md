# GitHub 涨星趋势投资分析框架

> 面向投资视角的**可复用分析流程**：把 GitHub 涨星数据转化为投资判断。
> 基于本项目 `tools/star_rank.js` 的涨速排名输出 + `star_history` 全量时序 + 联网检索，五步完成「信号 → 归因 → 验证 → 映射 → 过滤」。
> 每期（周 / 月 / 近 N 天）按本文档执行，产出投资人版分析结论与重点跟踪清单。

---

## 一、研究概述

| 项 | 说明 |
|---|---|
| 研究主题 | GitHub 涨星趋势的投资含义与后续跟踪重点 |
| 分析周期 | 每周例行（`--days 7`）、每月复盘（`--days 30`）、临时（近 N 天） |
| 分析领域 | 投资研究 / 行业研究（开发者工具与开源软件赛道） |
| 数据基础 | 本地 PostgreSQL `github_trending` 库 + 联网检索 |

**核心立场**：GitHub star 是"开发者关注度的**领先指标**"，不是"商业事实"。
它回答"有多少人愿意点一下星"，不回答"有多少人愿意付钱"。因此 star 增长必须经
过**归因 → 持续性验证 → 商业映射**才能转化为投资信号，不能把涨星直接等同于机会。

**核心研究问题**：
1. 本周涨星热浪集中在哪些赛道？驱动是事件炒作还是有机增长？
2. 哪些项目是"一次性脉冲"，哪些是"可持续爬坡"（最值得关注）？
3. 高增长项目里，哪些具备可投资/可跟踪的商业价值？

---

## 二、框架选择

| 章节 | 选用框架 | 应用方式 |
|---|---|---|
| 1. 信号拆解 | 赛道聚类 + STP | 按项目 solves/summary 聚类赛道，识别本周热浪结构 |
| 2. 驱动归因 | 事件归因分析 | 涨星拐点 vs 外部事件时间轴对齐，区分事件驱动/有机增长 |
| 3. 持续性验证 | 增长动量分析 + Gartner 炒作周期 | 日增曲线/加速度/拐点定位，判断处于加速/平台/回落 |
| 4. 商业映射 | 商业模式评估（简化）+ 波特五力 + TAM 粗估 | 评估变现路径、竞争格局与市场空间 |
| 5. 风险过滤 | 风险清单 | 排除刷量、一次性事件、大厂内部项目等噪音 |
| 6. 跟踪清单 | 指标卡 + 优先级矩阵 | 输出持续跟踪的项目与新增观测指标 |

---

## 三、分析管线总览

```
① 信号拆解 ──► ② 驱动归因 ──► ③ 持续性验证 ──► ④ 商业映射 ──► ⑤ 风险过滤
  本地数据       联网检索       本地时序+外部       联网检索         过滤噪音
  (赛道聚类)    (事件 vs 有机)  (核心:加速度/见顶)  (融资/模式/竞品)
                                      │
                                      ▼
                          输出：重点跟踪清单
```

- **①③ 主要用本地数据**（star_rank 排名 + `star_history` 全时序，免费即得）
- **②④ 需要联网检索**（WebSearch：发布/融资/社区/竞品）
- **③ 是投资判断核心**：单周暴涨可能是神话也可能是一次性新闻，只有曲线形状能区分

## 四、章节骨架

### 第 1 章 信号拆解

- **分析目标**：识别本周涨星热浪集中在哪些赛道，各赛道热度占比。
- **分析逻辑**：涨速 TOP N → 按项目 summary/solves 聚类赛道 → 统计赛道总增量与项目数。
- **核心假设**：涨星分布是赛道景气度的领先指标，热钱会先流向"开发者情绪"集中处。

#### 数据需求

| # | 数据项 | 类型 | 来源 | 获取方式 | 优先级 | 范围 |
|---|---|---|---|---|---|---|
| 1 | 近 N 天涨速 TOP N 列表 | 定量 | 本地 | `node tools/star_rank.js --days N --top 50` | P0 | 分析周期 |
| 2 | 每项目一句话总结 + 解决什么问题 | 定性 | 本地 | `trending_snapshots.summary/solves`（star_rank 已带 summary） | P0 | 最新 |
| 3 | 项目赛道标签 | 定性 | 本地 | 按 solves 关键词聚类（参考 `tools/analyze_stars.py` 分类规则） | P0 | 分析周期 |

#### 可视化计划
- **图 1**：水平条形图——各赛道本周总增量（X: 增量，Y: 赛道）
- **表 1**：赛道 × 项目数 × 总增量 × 平均增幅 对比表
- **论证结构**：What（热浪在哪几个赛道）→ Why（为什么这些赛道起量）→ So What（哪些赛道值得深挖）

### 第 2 章 驱动归因

- **分析目标**：判定每个高增长项目的涨星驱动是"事件炒作"还是"有机增长"。
- **分析逻辑**：对每个项目检索近 N 天外部事件（产品发布 / 大厂背书 / 营销 / 社区爆点），与涨星拐点时间对齐。
- **核心假设**：事件驱动的高峰 3-7 天内回落；有机增长曲线平滑可持续。

#### 数据需求

| # | 数据项 | 类型 | 来源 | 搜索关键词 | 优先级 | 范围 |
|---|---|---|---|---|---|---|
| 1 | 项目近 N 天发布/公告/release | 定性 | WebSearch / GitHub | `"{项目名}" 发布 OR release OR 上线` | P0 | 近 N 天 |
| 2 | 媒体报道 / 融资新闻 | 定性 | WebSearch | `"{项目名}" 融资 OR 新闻 OR 媒体报道` | P1 | 近 N 天 |
| 3 | 社区讨论热度（X/Reddit/HN） | 定性 | WebSearch | `"{项目名}" HN OR reddit OR X` | P1 | 近 N 天 |

#### 可视化计划
- **图 2**：时间轴——每项目涨星拐点 vs 关键事件时间点对齐
- **表 2**：项目 × 驱动类型（事件/有机/混合）× 证据
- **论证结构**：识别一次性脉冲来源 → 判断剩余"有机增长"项目

### 第 3 章 持续性验证（核心）

- **分析目标**：把高增长项目分为加速上升 / 平台整理 / 已见顶回落三档。
- **分析逻辑**：调出 `star_history` 全时序 → 计算每日增量、7 日均线、加速度（二阶导）、拐点；对比历史爆红项目曲线模式。
- **核心假设**：投资价值与"增速的可持续性"正相关；见顶回落项目不应进入跟踪重点。

#### 数据需求

| # | 数据项 | 类型 | 来源 | 获取方式 | 优先级 | 范围 |
|---|---|---|---|---|---|---|
| 1 | 项目完整采样时序 | 定量 | 本地 | `SELECT stars, fetched_at FROM star_history WHERE title=$1 ORDER BY fetched_at` | P0 | 全部 |
| 2 | 日增量 / 7 日均线 / 加速度 | 定量 | 本地计算 | 对时序做一阶/二阶差分 | P0 | 全部 |
| 3 | 涨速分档结果 | 定量 | 本地计算 | 加速：近 3 日日均 > 前 3 日日均；回落：峰值后持续下行 | P0 | 全部 |
| 4 | 历史爆红项目曲线模式库 | 定量 | 本地 | 从全部追踪项目时序中提取典型形态 | P1 | 全部 |

#### 可视化计划
- **图 3**：关键项目日增曲线折线图（多项目对比，7 日均线）
- **图 4**：涨速分档矩阵（加速/平台/回落 × 周增量）
- **论证结构**：曲线形态 → 持续性判断 → 决定是否进入第 4 章深挖

### 第 4 章 商业映射

- **分析目标**：对通过前两关的项目评估商业化成熟度与投资价值。
- **分析逻辑**：融资情况 → 商业模式（开源核心+云 / 企业版 / 托管 / 广告）→ 竞品格局 → 团队背景 → 市场空间粗估。
- **核心假设**：开发者工具赛道 "star 高 ≠ 商业化强"，付费意愿与免费用户规模分离。

#### 数据需求

| # | 数据项 | 类型 | 来源 | 搜索关键词 | 优先级 | 范围 |
|---|---|---|---|---|---|---|
| 1 | 融资轮次/金额/机构 | 定量 | WebSearch | `"{项目名}" 融资` | P0 | 全部 |
| 2 | 商业模式与付费产品 | 定性 | WebSearch / 官网 | `"{项目名}" pricing OR 付费 OR 企业版` | P0 | 最新 |
| 3 | 竞品格局 | 定性 | WebSearch | `"{项目名}" 竞品 OR competitor` | P1 | 最新 |
| 4 | 团队背景 | 定性 | WebSearch | `"{项目名}" team OR 创始人` | P1 | 最新 |
| 5 | 是否大厂内部项目 | 定性 | 本地+Web | 仓库归属判断（openai/anthropics/microsoft 等） | P0 | 最新 |

#### 可视化计划
- **图 5**：雷达图——融资 / 商业模式 / 社区活跃 / 竞争壁垒 / 团队
- **表 3**：商业化成熟度打分表（0-5 分制，分项打分 + 总评）
- **论证结构**：商业逻辑成立性 → 变现路径 → 估值想象空间

### 第 5 章 风险过滤

- **分析目标**：排除噪音项目，避免被虚假信号误导。
- **分析逻辑**：逐项检查刷量、改名、一次性营销、大厂内部项目、star 通胀。
- **核心假设**：过滤器应保守——不确定时标记风险而非进入跟踪清单。

#### 数据需求

| # | 风险项 | 判定方式 | 优先级 |
|---|---|---|---|
| 1 | star 刷量 | 曲线出现异常瞬时脉冲（单日增量远超平时数量级） | P0 |
| 2 | 改名/换仓库 | 项目名近期变更、内容与 star 历史不符 | P0 |
| 3 | 一次性营销事件 | 第 2 章判定为事件驱动且无后续动作 | P0 |
| 4 | 大厂内部项目 | 归属大厂，开放源码但无独立商业主体 | P1 |
| 5 | star 通胀（历史项目） | 老项目因榜单曝光重复进榜、增量来自存量 | P1 |

#### 可视化计划
- **表 4**：风险标记清单（项目 × 风险类型 × 证据 × 处置：保留/观察/排除）

### 第 6 章 输出：重点跟踪清单

- **分析目标**：产出下期可持续跟踪的项目与指标，回答"后面重点看什么"。
- **分析逻辑**：通过 ③④ 关 + 未被 ⑤ 排除的项目，按风险偏好（稳健/进取）分优先级。
- **核心假设**：跟踪清单是滚动更新的——每期重新跑 ①-⑤，动态进出。

#### 数据需求

| # | 数据项 | 类型 | 来源 | 说明 | 优先级 |
|---|---|---|---|---|---|
| 1 | 重点跟踪项目清单 | 定性 | 前五章输出 | 标注优先级（高/中/低）与跟踪理由 | P0 |
| 2 | 建议新增观测指标 | 定性 | 设计 | fork / issue 活跃 / release 频率 / 贡献者数量 / 是否出现付费产品 | P0 |
| 3 | 本地采样延续 | 定量 | 本地 | 现有 `node src/track.js daily/weekly/monthly` 持续写入 `star_history` | P0 |

#### 可视化计划
- **表 5**：跟踪清单（优先级 × 项目 × 赛道 × 跟踪指标 × 下期验证点）

## 七、执行说明

1. **每期执行**：先本地跑第 ①③ 步（数据齐全、快），再联网补 ②④，最后 ⑤⑥ 出结论。
2. **口径一致**：时间窗口（`--days`）与 TOP N 每期固定，保证跨期可比。
3. **零臆造**：所有数据标注来源；本地数据来自 `github_trending` 库，外部数据附检索出处；缺失数据明确标注"数据不可得"，不补造。
4. **跟踪清单滚动**：重点跟踪项目每期重评，自动进出。
5. **可追溯**：第 3 章分档结果可回溯到具体 SQL 与时序数据，第 2、4 章结论可回溯到检索来源。

## 八、执行流程与触发方式

> **触发词**：向 AI 提到"跑涨星分析 / 涨星周报 / star 趋势分析 / 分析涨星趋势"等，即按本节流程自动执行。

**完整执行流程（AI 按序执行）**：

1. **跑数据引擎**（本地 ①③ 步）：
   ```bash
   node tools/star_analysis.js --days 7 --top 50
   ```
   读取数据包：`tools/data/star_analysis_7d_<日期>.json`（排名 / 赛道热度 / 趋势分档 / 关键项目日增时序）。
2. **联网检索**（② 驱动归因 / ④ 商业映射）：对加速档与 TOP 项目逐一检索发布/融资/社区/竞品，聚焦框架第 2、4 章数据需求。
3. **生成报告**：按框架第 3-6 章组织，产出投资人版周报，保存到 `docs/reports/STAR_TREND_REPORT_<日期>.md`（结果物报告统一归档在 `docs/reports/`，与项目文档 `docs/` 分离），关键数据用图表呈现，参考文献按 GB/T 7714 标注。

**参数约定**：周报固定 `--days 7 --top 50`；月报 `--days 30 --top 50`；口径一致保证跨期可比。

**自动化边界**：本地数据（①③）已脚本化；联网检索与报告撰写需 AI 执行（联网/LLM），无法纯脚本替代。
